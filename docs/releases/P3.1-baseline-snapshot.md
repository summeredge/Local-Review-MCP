# P3.1 Single-Workspace Closure Audit

Audit date: 2026-09-13

Scope: the current `main` checkout, one registered workspace, and the existing
Control Plane recovery path. No new public interface, state model, scheduler,
webhook, external Codex hook, or multi-workspace behavior was added.

## Audit scope

The audit followed the production call chain rather than treating each record
as an isolated feature:

```text
Goal
  -> Task
  -> Controlled Actuation / Execution
  -> AutoIteration
  -> Execution Routing
  -> ReviewRequest
  -> ConversationRouting
  -> ReviewDelivery
  -> ExtensionDelivery
  -> Extension Review Completion
  -> ReviewResult
  -> ReviewVerdict
  -> Goal terminal state
```

The checked identity chain is exact at every boundary:

```text
workspace_id
  -> task_id
  -> execution_id
  -> review_request_id
  -> routing_id / delivery_id
  -> conversation_id
  -> review_result_id
```

Persisted records are still owned by their existing services and paths:

| Record | Durable owner and location |
| --- | --- |
| Goal | `control-plane/goal-orchestrations.json` |
| AutoIteration | `control-plane/auto-iterations.json` |
| Actuation authorization / reservation | `control-plane/controlled-actuations.json` |
| Task | `.task/contexts/<task_id>.json` |
| Execution | `.task/executions/<workspace_id>/<task_id>/<execution_id>.json` |
| ReviewRequest | `.task/review_requests/<workspace_id>/<review_request_id>.json` |
| ConversationRouting | `.task/conversation_routings/<workspace_id>/<routing_id>.json` |
| ReviewDelivery | `.task/review_deliveries/<workspace_id>/<delivery_id>.json` |
| ReviewResult | `.task/review_results/<workspace_id>/<result_id>.json` |
| ReviewVerdict | Derived only from the matching completed `ReviewResult` content |
| ExtensionDelivery | `control-plane/extension-deliveries.json` |
| Extension Review Completion | `control-plane/extension-review-completions.json` |

## Verified flows

- Normal closure: one Goal, Phase, and Task reaches `Execution = passed`, one
  ReviewRequest is routed and delivered, one Completion produces one
  ReviewResult, `APPROVE` is parsed, and the Goal becomes `completed`.
- `ITERATE` preserves the same Goal/Phase/Task, advances the AutoIteration
  counter, creates the stable next Execution identity, and reaches the existing
  second-review path.
- `HUMAN_REQUIRED` remains terminal and does not start another Execution.
- Failed Execution remains failed and does not create a ReviewRequest.
- Review, Routing, Delivery, Result, and Verdict identity conflicts fail closed.
- An already completed Goal remains terminal and does not execute, review, or
  create another Goal after recovery.

## Recovery coverage

The startup order is preserved after the existing HTTP, OAuth, Bridge, and
durable outbox prerequisites:

```text
Codex Execution recovery
  -> AutoIteration recovery
  -> Goal Orchestration recovery
  -> Execution Routing recovery
  -> Runtime ready
```

Each recovery layer only advances its own durable evidence. Codex recovery
reconciles persisted `running` Executions and never starts Codex. AutoIteration
resumes a stable checkpoint, reuses existing Review/Routing/Delivery/Result
records, and replays terminal notifications. Goal Orchestration advances a
running checkpoint only; pending and terminal Goals are not auto-started.
Execution Routing scans passed orphan Executions and enters the existing review
workflow, while skipping already-associated chains.

Every startup recovery call is independently guarded. A failed recovery layer
is logged and leaves the local MCP Runtime available; it does not erase or
overwrite lower durable state.

The following restart and idempotency cases are covered by the existing Control
Plane, completion, routing, OAuth, and integration tests:

| Scenario | Result |
| --- | --- |
| A. Goal -> passed Execution -> Review -> `APPROVE` -> Goal complete | Pass |
| B. Passed Execution without ReviewRequest -> recovery | Creates Review once; no second Codex spawn |
| C. ReviewRequest already persisted -> recovery | Reuses it; no duplicate request or delivery |
| D. Completion/ReviewResult persisted -> recovery | Reuses one Result, repairs ReviewRequest status, and continues to Verdict |
| E. Goal already `completed` -> recovery | State and all lower evidence stay unchanged |
| F. Repeated recovery / duplicate terminal signals | Stable durable snapshot; no duplicate Goal, ReviewRequest, Completion, or Result |
| OAuth Registry / Client restart and reset | Existing scoped persistence and reset semantics preserved |

## Idempotency fixes made during audit

Two concrete defects were found by new regression assertions and fixed at the
smallest shared boundaries:

- `ReviewCompletionRouter` coalesces concurrent collection for one workspace
  and routing, and repairs a non-terminal ReviewRequest when a completed result
  is already present.
- `ReviewResultService` coalesces concurrent creation for one workspace and
  ReviewRequest, keeping one effective Result. AutoIteration also reconciles
  the ReviewRequest status before parsing a recovered Result.

No state transition, public contract, OAuth/Connector protocol, Extension
identity rule, or MCP Data Plane boundary was changed.

## Known non-blocking limitations

- The audit uses the repository's deterministic fake Codex, Browser Worker, and
  Extension actors for repeatable restart tests. It does not certify a live
  logged-in ChatGPT/Fiber session or a real external Extension installation.
- The baseline is intentionally single-workspace. Multi-workspace scheduling,
  external webhook delivery, and CI/external Codex hooks remain out of scope.
- One existing test is intentionally skipped by the repository's current test
  suite; no closure test is skipped.
