# P5.8 Desktop Capability Activation Bootstrap

## Architecture

P5.8 freezes on Desktop Capability Activation Bootstrap:

```text
Desktop cold start
    ↓
CODEX_CLI_PATH -> DesktopBootstrapTrampoline
    ↓
capture CODEX_APP_TOOLS_PIPE_PATH
    ↓
POST /launcher/desktop-tools-pipe
    ↓
pending handoff while Desktop owner identity is absent
    ↓
已有可信 Desktop thread binding 时，一次性 deep link 激活
    ↓
Desktop IPC activation binding
    ↓
owner-bound promotion
    ↓
pipeSource=handoff
```

The pending value is authenticated loopback evidence, not an executable
capability. It is never returned to the resolver until the Desktop IPC observer
supplies the owner identity. Pending evidence expires and is discarded on TTL,
disconnect, or owner mismatch.

## Supported user operation

当 Desktop IPC 已连接、Tools Pipe 为 pending 且 `ownerClientId` 尚未建立时，LRM
从当前 workspace 的正式 `DesktopThreadBindingStore` 选择 `updated_at` 最新的有效
binding，打开一次 `codex://threads/<target_thread_id>`。时间相同时按 session 文件名排序。
绑定必须通过既有 schema、backend、workspace/session 校验；损坏条目跳过。
`currentConversationId` 可能由 following/conversation 事件提前写入，不能作为 owner identity 已就绪的依据。
同一连接生命周期最多尝试一次；owner 已建立后不再导航，断开后新生命周期允许重新尝试。
异步读取期间若 owner 已建立、Desktop 断开、handoff 不再 pending 或 runtime 关闭，取消导航。
deep link 成功只表示导航请求完成；ready 仍由现有 IPC owner binding 和 handoff promotion 判定。
Launcher 显示以下过渡状态：

```text
Desktop IPC: Connected
Desktop Identity: Waiting for activation
Tools Pipe: Pending
Capability: Waiting for Desktop activation
```

After activation and promotion:

```text
Desktop IPC: Connected
Desktop Identity: Ready
Tools Pipe: Active
Capability: pipeSource=handoff
```

## Runtime restart recovery

The handoff is maintained for the whole lifetime of the spawned `codex.exe`, not just at cold start.
After the first `accepted` or `pending` answer the trampoline probes
`/launcher/desktop-tools-pipe/probe` on a low frequency interval and re-offers the pipe it captured at
launch whenever the probe stops proving the capability:

```text
MCP Runtime restarts (Desktop keeps running)
    -> handoff evidence is gone with the old process
    -> probe reports unavailable / cannot connect
    -> re-POST the inherited CODEX_APP_TOOLS_PIPE_PATH
    -> LRM owner binding accepts, or stages pending until the owner is back
    -> probe healthy, pipeSource=handoff
```

Recovering this way does not require a new conversation, re-activating a conversation, or restarting
Codex Desktop. Those remain supported compatibility paths, but they are not what restores the
capability after an MCP runtime restart.

`handoffDeadlineSeconds` bounds the first cold-start retry burst only. Maintenance continues while the
child runs, because an MCP runtime restart is not a Desktop restart. A `400/401/403` answer is treated
as deterministic and stops the loop instead of retrying forever; connection failures, `409` and `5xx`
retry on a bounded backoff.

## Not supported

首次使用没有历史可信 binding 时保持 fail-closed，等待用户选择已有会话或现有 fallback。
导航失败不重试、不创建 thread，也不使用 `codex://threads/new?prompt=...`。
本路径不新增 Desktop instance identity 或 IPC 协议。

## 安装与修复

Launcher 调用的 `scripts/start-production.ps1` 在构建成功后自动运行幂等 setup，
构建现有 trampoline、更新受限权限且被 Git 忽略的 `trampoline.config.ini`，并设置用户级
`CODEX_CLI_PATH`。token 取自 runtime 同样优先的 `LOCAL_REVIEW_MCP_TOKEN` 或配置文件，
不会进入命令参数或日志。配置变更后，已运行的 Codex Desktop 需完整退出后重新启动。
setup 失败保留现有 fallback；`-SkipDesktopBootstrap` 可跳过安装，供独立部署及隔离测试使用。

## Windows cold-start E2E 验证

使用已有合法 durable Desktop thread binding 的 workspace，从 Launcher 正常启动生产服务，
等待自动 setup 完成后，完整退出并重新打开 Codex Desktop，期间不手动切换会话或创建 thread。
确认 Launcher 从 `Tools Pipe: Pending` 自动转为 `Desktop Identity: Ready`、`Tools Pipe: Active`，
最终 capability 为 `pipeSource=handoff`，且同一次连接不会重复导航。
无需手工设置环境变量或创建 INI；没有历史 binding 的首次使用仍按 fail-closed/fallback 验证。

## Security boundary

The trampoline does not infer ownership from `sourceClientId`,
`initialize.clientId`, a pipe name, or process injection. It does not weaken
authentication or modify Desktop IPC. LRM remains fail-closed until the
existing Desktop owner binding is observed.

Maintenance does not change that boundary. It re-offers the same inherited
`CODEX_APP_TOOLS_PIPE_PATH` and lets the existing owner binding decide, so a
recovered handoff still travels `stagePending` -> `owner_bound` -> `promoted`
whenever the owner identity is not yet back. The pipe path is never persisted to
disk, a config file, LRM state, or the trampoline log; only `pipe_present` is
recorded. `DesktopToolsPipeHandoff` owner binding, pending TTL, disconnect and
owner-mismatch cleanup, and the `DesktopToolsPipeResolver` fail-closed behaviour
are unchanged.
