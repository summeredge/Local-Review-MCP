# P5.9 Desktop Capability Negotiation & Execution Fallback

Interactive execution keeps the Desktop provider as the first choice and uses
the existing private app-server as the standalone provider when Desktop cannot
establish a capability.

```text
interactive Goal
    -> capability negotiator
    -> Desktop provider
       -> existing trampoline / SessionStart handoff evidence
       -> Desktop codex_app execution
    -> capability failure -> GUI recheck / standalone choice
    -> 5 minute AFK window with no user action -> standalone provider
       -> private codex app-server execution
```

The negotiator exposes these states through the authenticated loopback
`/launcher/capability` endpoint:

| State | Source | Meaning |
| --- | --- | --- |
| `initializing` | — | No execution choice has been made yet. |
| `desktop_pending` | `desktop` | The Desktop handoff/capability is being checked. |
| `desktop_ready` | `desktop` | Desktop can execute the request. |
| `desktop_failed` | `desktop` | Desktop capability failed; `recheck` and `standalone` are available. |
| `fallback_ready` | `standalone` | Standalone fallback selected; `reason` says whether the user or the AFK window did it. |
| `fallback_running` | `standalone` | Standalone execution is in progress. |

Each snapshot is associated with an `execution_id`, `task_id`, and optional
`actuation_id`. The authenticated endpoint accepts `?execution_id=<id>` or
`?execution_id=current`; actions must target the execution they change. The
launcher displays that execution, source, state, and provides
**Retry Desktop** and **Use Standalone** actions. Recheck only reads the
existing Desktop capability again; it never triggers a new handoff. A failed
Desktop attempt waits for the user for `fallbackAfkTimeoutMs` (default 5 minutes).
The user choosing first wins; if the window expires with no action, standalone is
selected for them. If Desktop recovers before then, the fallback timer is
cancelled and no backend migration happens.

The AFK window records which side chose standalone, so the two sources stay
distinguishable in the snapshot, the timeline, and the launcher:

| `reason` | Source | Timeline event |
| --- | --- | --- |
| `user_selected_standalone` | The user pressed **Use Standalone**. | `fallback_user_selected` |
| `afk_fallback_timeout` | No user action for `fallbackAfkTimeoutMs`. | `fallback_afk_timeout` |

The failure snapshot keeps `state`, `source`, `reason`, and `error_code`.
While the decision is pending, its `timestamps.fallbackDeadlineAt` is exposed
so the launcher can show the remaining time. The existing capability timeline
records the decision path with `desktop_pending`, `desktop_failed`,
`fallback_waiting`, `fallback_user_selected` or `fallback_afk_timeout`, and
`fallback_running` events.

`ExecutionBackend`, Desktop IPC, SessionStart hooks, the trampoline, handoff
contract, and `codex_app` protocol are unchanged. The provider layer only
selects the existing execution backends and exposes bounded state transitions.
